## 三、初检问题与关闭状态

> 本节保留 2026-09-02 初检的证据和原因，便于追溯；问题状态以第十节和本报告顶部的当前执行快照为准。未特别标注的旧描述不是当前代码状态。

### BUILD-01：正式服务器引用的内容产物当前不存在

`apps/api/src/v11-server.ts` 固定读取 `content/compiled/v1.2.0.json`，但当前工作区的 `content/compiled/` 只有 `v1.1.0.json`。已经运行的旧进程可能暂时掩盖问题；V11 API 重新启动时会因正式内容文件缺失而失败。这也会让“当前内容版本、客户端 bundled 内容和发布清单”无法形成同一真相。

必须先生成并核验当前候选内容产物，或把服务器配置改为从经过校验的发布清单选择内容文件；不得简单回退到 v1.1.0 继续使用。

### FLOW-01：刷新后远程动作 ID 从头开始，幂等键会撞上旧动作

证据：

- `V11RemoteStudentFlow` 的 `actionSequence` 构造时固定从 0 开始。
- 正式页面刷新只从服务端读取经营状态，没有恢复动作序号。
- 动作 ID 和幂等键都使用 `remote-action-00001` 这一序号。
- 服务端发现相同幂等键后直接返回旧日志，没有校验“同一幂等键是否仍是同一个动作”。

本次诊断复现：先用 `remote-action-00001` 提交序章，再模拟刷新后用同一键提交调查。服务端返回的仍是 `onboarding_completed` 日志，调查没有执行，行动力仍为 4。界面却可能根据新动作显示“已经完成”的提示。

这能够直接解释“点了选项或调查，但流程没有继续/结果缺失”的一类卡死。

### FLOW-02：正式服务器使用内存存储，重启会清空全部游戏数据

证据：

- `apps/api/src/v11-server.ts` 直接创建 `V11MemoryStore`。
- 班级、学生、会话、首局、动作日志、状态和报告都只保存在进程内的 `Map` 中。
- 当前没有正式 `V11PostgresStore` 实现。

结果是服务重启、电脑休眠后进程退出或发布替换进程时，学生会话和首局都会消失。这不符合“首局不可覆盖、动作可审计、课堂中断后可恢复”的绝对不变量。

### FLOW-03：正式流程没有持久化页面栈，章节复盘可以被刷新跳过

正式 `/v11` 只在 `localStorage` 保存 token、playthroughId 和种子，没有保存页面步骤；恢复时根据少量状态重新猜页面。

本次诊断复现：R12 结果确认后、年度章节复盘尚未确认时刷新，远程流程把页面恢复为 `complete`，而不是 `chapter-review`。同时：

- `ending` 已存在；
- 服务端报告仍未生成，因为年度复盘未确认；
- 页面恢复逻辑会立即请求报告；
- 报告返回 404 后，最外层恢复逻辑会删除本地会话。

R02、R06、R09 的章节复盘刷新后也会直接进入下一轮简报，只是不会触发报告错误。

### FLOW-04：没有正式 outbox；响应丢失时可能重复扣资源

正式远程流程直接 `fetch`，没有先把用户意图以稳定命令 ID 写入 IndexedDB outbox。若服务端已经执行调查，但响应在途中丢失：

1. 客户端仍认为调查未完成；
2. 玩家重试时会生成新的动作 ID 和幂等键；
3. 规则引擎没有禁止同一轮重复执行同一个 `stageActionId`；
4. 同一调查可能再次扣现金、行动力和时间。

正式提交的响应丢失通常会进入“请先确认本轮结果”错误，刷新后可能找回；调查动作则存在真实重复结算风险。

### RULE-01：结果页指标变化与正式状态不一致

事件的即时效果先被加入 `immediateEffects`，生成 `metricChanges` 时又从 `triggeredEvents` 追加一次，因此被重复统计；事件的延迟效果也会过早进入本轮变化摘要。

本次诊断复现 `r01-tourist`：

- 正式状态实际变化：知名度 `+16`、购买转化 `+4`；
- 结果页数据：知名度 `+20`、购买转化 `+4`。

这会同时污染结果页、预判命中和“影响最大的一轮”报告判断。

### RULE-02：规则引擎和报告引擎使用两套评分公式

- 规则引擎在 `v11-scoring.ts` 计算正式 `scoreBreakdown`。
- 报告引擎在 `v11-report.ts` 重新计算另一套 survival、consistency 和等级阈值，没有使用正式状态中的评分。
- 报告公式没有 `out_of_control` 等级；极差状态在引擎中为“经营失控”，报告中仍会显示“勉强活着”。

本次抽样状态中，规则引擎给出总分 55，报告给出总分 61。两者等级此时相同，但在低分状态会直接产生不同等级。

### FLOW-05：前后端只比较版本号，没有真正使用校验和建立一致性

- API 已提供内容版本和 SHA-256 校验值。
- 正式 Web 仍使用构建时打包的 `v11FullContent`。
- 加入和恢复只比较 `contentVersion`，返回的 `contentChecksum` 没有参与校验。

因此，只要前端和服务端恰好使用相同版本号但内容不同，界面仍可能展示一个方案，服务端却按另一份内容结算。此前出现过的“本地有视觉路线、线上没有”的问题在架构上尚未完全封死。

## 四、P1：核心游戏感和反馈闭环未达标

### BAL-01：行动力已经防止死局，但也削弱了真实取舍

- 内容中已有 2—4 点的方案成本，但此前被编译和结算为统一 2 点，造成显示、规则和可达性不一致。
- 每轮现在保留 4 点战略行动力，调查使用独立的 4 点自由行动力，方案按复杂度实际消耗 2—4 点。
- 12 轮中有 10 轮，三项调查的行动力总和正好等于全部 4 点；玩家可以查完所有事情后仍无条件提交任意方案。
- 只有 R03、R11 的调查总成本为 5，无法全部完成。

这与目标“至少 80% 轮次不能查完全部信息再执行最复杂方案”相反。当前主要取舍变成“要不要留一点给风险预案”，而不是调查、测试、预案和战略执行共同竞争资源。

### BAL-02：现有 50,000 局模拟不能证明没有支配策略

模拟器用确定性均匀索引随机挑选可负担方案，因此每项约 20% 是选择器本身造成的，不是玩家策略或收益比较的结果。它没有模拟：

- 调查组合；
- 风险预案；
- 关键预判；
- 视觉测试；
- 跳过策略；
- 证据优先、现金保守、增长优先等不同玩家策略。

最低期末现金仍有 266,088 元，说明当前随机路径没有形成明显现金危机。模拟结果中还有 1.52% 已完成十二轮却得到 `unfinished`，但发布门只统计“结局 ID 数量”，把 `unfinished` 也算进了分布。

### PROG-01：路线和结局没有兑现目标中的长期路径感

- 路线算法只有社区关系、视觉系统、平台增长、实验探索 4 类；目标中描述的文化精品、高效率大众、小众忠诚等路线尚未独立形成。
- 多数结局只要求某一轮选择成立，再加上通用的“完成至少 3 轮/两个维度超过 35”门槛；完成十二轮后，单个早期选择仍可能通过数组优先级决定最终结局。
- `endingTitle` 已进入报告数据，但学生完成页和报告页没有显示它，18 个结局定义在玩家体验中基本不可见。
- `victoryConfig.successLevel` 没有参与最终胜负判断；PRD 中现金归零或履约崩溃的等级封顶也未实现。

### FB-01：已经结算的奖励和风险反馈没有在该出现的地方出现

- `newAchievements` 已由规则引擎产生，但单轮结果页没有渲染；玩家只能在章节复盘看到累计成就，而且会重复看到以前章节的成就。
- 正式选择的 `riskOutcome` 已结算，但普通选择结果页优先显示方案的 `delayedRisk`，没有显示预案究竟生效、浪费还是没有触发。
- 预判反馈藏在折叠区域，且依据受 `metricChanges` 重复统计影响。

因此，玩家付出的调查/预案成本与即时能力感之间仍有断层。

### VIS-01：视觉测试的说明、成本和作用不一致

- 界面写“免费测试 · 不占行动力”，规则引擎实际扣 1 点自由行动力。
- 按钮没有在行动力不足时禁用，玩家可能点击后收到规则错误。
- 测试只记录 touchpoint ID 并改变前端的缩小/黑白/遮挡展示，没有形成结构化诊断或经营修正。
- 内容包声明 6 套视觉系统，正式界面只展示 `v-line`、`v-symbol`、`v-hand` 3 套；另 3 套不可由玩家选择，却被发布报告统计为已完成内容。

结合最近明确要求“三个正式方案”，当前合理方向应是把生产协议收敛为 3 套真正可选、可测试、可结算的方案，而不是保留 3 套不可达数据制造数量达标。

### COPY-01：新版行动界面没有完整使用内容模型

每轮内容已经提供两个 `decisionQuestions` 和 `knownFacts`，但当前实际使用的 `ActionCenterV14`：

- 只读取第一个问题；
- 把全部行动平铺在该问题下；
- 不显示第二个问题的 context；
- 不显示 `knownFacts`。

这会让“眼前发生了什么”再次退化成一个泛标题，削弱每轮现场差异。旧版 `ActionCenter` 能显示这些信息，但已经不是实际渲染路径。

### REPLAY-01：首局不可覆盖已实现一半，重玩流程尚未打通

数据类型中存在 `first_run | replay`，但当前 V11 API 没有创建 replay 的学生接口，完成页也没有重玩入口。玩家无法在不污染首局的前提下进行反事实重玩。

## 五、发布门仍未完成

以下工程与项目终审门仍未完成。组织真人试玩已按项目负责人决定取消，不再列为发布阻断项，也不把自动化结果冒充真人结论：

- 12 轮中文、地域文化、价格、理论因果和视觉术语的项目负责人终审；
- 六类策略代理的完整动作、重放、资源、路线和报告一致性验证；
- 真实 iPhone、Android、微信内置浏览器测试；
- 生产 HTTPS、校园网络、数据库重启/备份/恢复和 80 人真实发布演练。

真实新玩家上手、35—50 分钟实际时长、趣味与教学理解不再作为本版本放行条件，统一列入“未经组织试玩验证”的已知风险。

`docs/v1.1-release-candidate-report.md` 记录的是 2026-08-27 的旧候选状态，且仍引用 `v1.1.0`。它不能继续作为当前 `v1.2.0` 的发布结论。

## 六、改进计划

计划遵守“一次改动只对应一个任务 ID”。每项只为已确认缺陷补针对性回归，复用现有测试与模拟，不新增截图堆积或无意义测试。

### 第一批：先消除正式流程丢失和重复结算（P0）

#### FLOW-01：稳定命令 ID、幂等冲突检测与 live outbox

实现：

- 用户点击正式动作时先生成一次稳定 `clientCommandId`，写入 IndexedDB outbox，再发送。
- 超时、刷新和重试继续发送同一命令，不生成新幂等键。
- 服务端为幂等记录保存动作摘要；同键同动作返回原结果，同键不同动作返回明确冲突，不能静默返回旧日志。
- 规则层拒绝同一轮重复执行同一个 stage action。
- 所有网络异常转为明确中文状态，不再直接显示 `Failed to fetch`。

验收：分别模拟“请求未到服务端”“服务端已结算但响应丢失”“刷新后重试”；现金、行动力、时间和日志均只变化一次。

#### FLOW-02：V11 正式持久化存储

实现：

- 按现有数据库协议实现 `V11PostgresStore`，正式服务器不再使用 `V11MemoryStore`。
- 班级内容版本/种子不可变；首局、重玩、动作日志和快照追加保存。
- 内存实现只保留单元测试和显式 demo 模式。

验收：学生进行到任意行动、待确认结果、章节复盘和报告后分别重启 API，重新进入仍得到同一动作日志、状态哈希和页面阶段。

#### FLOW-03：统一恢复状态机

实现：

- 建立唯一 `deriveResumeScreen(state, reportAvailable)`：优先级为待确认结果 → 待确认章节复盘 → 完成/报告 → 当前轮简报。
- 服务端公开 `chapterReviewPending`、`reportAvailable` 和下一命令序号/游标。
- 本地 UI checkpoint 只保存 action/choice/detail/dashboard 等非权威界面状态；与服务端冲突时以服务端阶段为准。
- 只有 `reportAvailable=true` 才请求报告；暂时失败不能删除会话。

验收：R02、R06、R09、R12 复盘页和每种普通页面刷新均恢复正确；R12 刷新不会退出首局。

#### FLOW-04：正式内容来源和校验和一致性

实现：

- 正式 `/v11` 从 API 加载已发布内容，或在进入前严格比较前端包与 API 的 SHA-256。
- 版本相同但校验值不同必须阻止进入并显示中文更新提示。
- `/v11-full`、`/v11-slice` 可继续使用本地预览内容，但明确标记非正式局。

验收：人为构造同版本不同内容，客户端必须在任何动作提交前拒绝进入。

### 第二批：统一结算真相和即时反馈（P0/P1）

#### RULE-01：结果、评分和报告只使用一套正式计算

实现：

- 修复事件即时效果重复计数和延迟效果提前展示。
- 把评分等级阈值、现金/履约封顶规则写入单一规则函数；报告直接使用正式 `state.scoreBreakdown`。
- 预判、“影响最大的一轮”和教师分析均读取修正后的实际变化。
- 对所有完成路径配置确定结局，不允许 `unfinished` 被当作合法结局计数。

验收：每轮 `result.metricChanges` 必须等于正式状态前后差；报告分数/等级与服务端状态逐字段相同；现金或履约严重失败时等级按规则封顶。

#### FB-01：把已经结算的反馈放回单轮结果页

实现：

- 结果页即时显示新成就、风险预案状态和关键预判结果。
- 章节复盘只显示本章新增成就，不重复累计列表。
- 完成页展示经营等级、路线称号和实际结局标题，并解释三者区别。
- 结局条件改为真实多轮组合，不用单一选择和数组优先级决定整局身份。

验收：预案生效、未触发、未选择三条固定路径均能在当轮看懂；每个结局至少回指三个轮次或两个明确维度。

### 第三批：恢复经营取舍和视觉测试价值（P1）

#### BAL-01：重做行动力与经济平衡验证

实现：

- 恢复内容中 2—4 点的战略方案差异，取消编译阶段强制写成 2 点。
- 用服务器的“执行后至少保留一种可提交/可跳过出口”检查防止死局，不再通过固定预留池抹平所有取舍。
- 校准调查、风险预案、战略投入、经营收入和固定支出，使现金安全、现金吃紧和经营失败均可达且可解释。
- 扩展现有 `simulateV11`，加入证据优先、现金保守、增长优先、风险管理、跳过等确定性策略代理；移除“随机选择份额≈20%即无支配策略”的错误代理指标。

验收：至少 80% 轮次不能同时完成全部行动和最高消耗方案；所有路线均可完成；期末现金和经营等级形成有区分度的分布；没有一个方案在多数可达状态下全面优于同轮其他方案。

#### VIS-01：让三套正式视觉方案可测试、可解释、可结算

实现：

- 正式内容只保留当前已批准且界面可达的三套方案；其他实验系统移出生产统计。
- 视觉测试明确显示真实的 1 点成本，并在行动力不足时禁用并说明原因。
- 每项测试返回结构化诊断：哪一触点通过、哪一触点失效、为什么、支持/质疑哪条视觉路线。
- 诊断进入 trace、结果页和报告；视觉匹配至少影响一项可解释结果，而不只改变 CSS 预览。

验收：三套方案在相同店招、杯身、包装和头像机位中比较；每套至少在一种经营路径占优、在一种路径受限。

#### COPY-01：让当前经营现场真正使用两组问题和已知事实

实现：

- `ActionCenterV14` 渲染全部 `decisionQuestions`，按问题分组行动并显示对应 context。
- 在不增加长页面的前提下显示 1—2 条 `knownFacts`，调查后把新事实放入可回看区。
- 逐轮检查“现场—为什么现在—两难—两个问题—行动结果”是否指向同一经营冲突。
- 完成 `docs/content-review-v11.md` 的项目负责人终审，不再以 Schema 通过代替中文和教学判断。

验收：项目负责人从正式页面逐轮确认每轮正在发生什么、为什么现在必须决定，以及至少两项行动分别回答什么；未确认项必须改写或登记为发布风险。

### 第四批：补齐重玩和正式发布门（P1/Release）

#### REPLAY-01：首局与重玩正式分离

实现：完成报告后允许创建 `replay`；新 playthrough 使用独立 ID、日志和报告，教师分析默认以 `first_run` 为正式记录并可对照重玩。

#### RELEASE-01：直接建设、工程验收与版本冻结

验收：所有脚本化路径完成 12 轮且无卡死；至少形成 3 条机制上可辨认的路线；正式状态、页面与报告一致；项目负责人完成内容终审；生产重启不丢数据。取消组织真人试玩后，不再把“真实玩家理解、情绪、节奏和教学效果已验证”作为发布结论。

## 七、发布前建设计划

> 补充任务 ID：`RELEASE-PLAN-01`。适用对象为当前候选版。目标是把项目从“本机可演示”推进到“工程上可部署、可恢复、可追溯和可回退”，不扩展玩法数量，不新增装饰页面，也不以堆积测试数量代替风险验证。2026-09-02 起采用**直接建设模式**：取消组织 3—5 人和 8—12 人试玩，以风险定向自动化、策略代理、项目负责人走查和真实设备关键链路替代。

### 7.1 建设原则

1. **先保证候选版可启动，再修结算真相。** `BUILD-01`、`FLOW-01—04` 和 `RULE-01` 未关闭前，暂停新增配图、动画、选项和章节。
2. **一个任务只解决一个缺陷编号。** 数据、规则、内容改动分别带上必要迁移、受影响测试和文档，不进行顺手重构。
3. **只验证真实风险。** 新增验证必须对应本报告已发现的失败模式：重复提交、响应丢失、刷新错位、进程重启、内容不一致、错误评分、资源死局或真机布局阻断。
4. **发布证据必须来自候选产物。** 修复前的 v1.1/M15 记录只作历史参考；正式放行必须使用同一个候选提交、内容校验和、数据库迁移版本和部署配置重新生成证据。
5. **历史日志不可回滚。** 应用可以回退到上一镜像，首局动作、快照和报告不得覆盖；内容修正只能发布新版本并创建新班级。
6. **不把自动化当成真人反馈。** 自动流程可以证明可达性、确定性和数据正确性，不能证明文案一定被理解、体验一定有趣或课堂讨论一定有效；这些未验证项进入发布风险声明，不伪造为“通过”。

### 7.3 A 阶段：把每次操作变成可恢复的正式命令

#### A0. 候选版本与内容产物对齐（`BUILD-01`）

- 确认当前正式候选版本号；重新执行内容编译，生成与代码声明一致的只读内容文件和校验和。
- `v11-server.ts` 不再依赖一个未经发布检查确认的硬编码缺失路径；启动时输出版本、校验和和资产清单状态，任一不匹配即拒绝 readiness。
- Web bundled 内容、API 正式内容、班级绑定版本和发布清单必须引用同一版本与校验和。

退出证据：干净进程可以启动 V11 API；`/content` 返回的版本与 SHA-256 和本地发布清单一致；删除或篡改产物时服务明确拒绝启动，不以 `Failed to fetch` 留给玩家猜测。

#### A1. 动作协议与 outbox（`FLOW-01`）

- 客户端为每个动作生成跨刷新稳定的 `commandId`、单局递增 `sequence` 和动作内容哈希；未确认命令写入 IndexedDB outbox。
- 服务端把 `(playthroughId, commandId)` 作为幂等边界；同 ID 同内容返回原结果，同 ID 不同内容返回冲突，不得静默复用旧动作。
- 调查、预测、视觉测试、选择、结果确认和章节确认都使用同一命令协议；已调查动作增加业务级唯一约束，避免响应丢失后重复扣费。
- 仅补充五个故障场景：提交前断网、服务端已写入但响应丢失、重复点击、刷新后重试、两设备同时恢复。不得为未发生的组合堆测试。

退出证据：动作日志序号连续；重复请求只留一条结算；现金、行动力和时间只变化一次；冲突提示为玩家可理解的中文。

#### A2. PostgreSQL 正式存储（`FLOW-02`）

- 用 `V11PostgresStore` 替代正式入口的 `V11MemoryStore`；内存实现只保留给单元测试和本地样例。
- 建立班级版本/种子不可变、首局唯一、动作序号唯一、幂等键唯一、报告唯一等数据库约束；迁移只新增，不覆盖已有历史。
- 在预发布环境完成“游戏进行到第 6 轮 → 重启 Web/API/数据库连接 → 恢复并完成”的演练。

退出证据：重启前后动作数、状态哈希、现金账本和待处理事件一致；随机抽取一局可由追加日志重放得到相同报告。

#### A3. 唯一恢复状态机与内容校验（`FLOW-03`、`FLOW-04`）

- 服务端快照明确返回 `nextRequiredState`、待确认结果、待章节复盘、报告可用状态和最后确认序号；客户端不再分别猜测恢复页面。
- 恢复失败分为会话失效、内容版本冲突、临时网络异常和数据冲突；临时错误不得删除本地会话。
- 客户端必须验证 `contentVersion + contentChecksum`；不匹配时停止提交并刷新正式内容，不能继续使用同版本不同内容。

退出证据：12 个回合分别在经营现场、结果页、章节复盘前后刷新均回到唯一正确状态；R12 不会提前进入完成页或因报告尚未生成而退出登录。

#### A4. 唯一结算与评分源（`RULE-01`）

- 即时事件只计入一次；延迟事件只在实际触发时显示和结算。
- 报告读取规则引擎已确认的评分、路线和结局，不再用另一套公式重算。
- 将 PRD 分数区间及现金归零、交付严重失控封顶规则固化为一处可版本化规则。

退出证据：同一局的正式状态、结果页、章节复盘、教师视图和最终报告对每项指标、现金、评分、路线和结局完全一致。

### 7.4 B 阶段：完成玩家可感知的经营闭环

#### B1. 收益、风险和成就反馈（`FB-01`）

- 每轮结果明确分开“本轮投入、经营收入、净现金变化、非现金影响”；收入图只作激励背景，具体数值由界面文字渲染。
- 结果页显示风险预案是命中、浪费、未覆盖还是未触发，并即时显示本轮新成就；章节复盘只汇总本章新增内容。
- 完成页必须展示经营等级、路线名、结局名及两条可回指本局动作的因果，不再让 18 个结局只存在于数据中。

#### B2. 资源和平衡（`BAL-01`）

- 恢复 2—4 点行动力差异与现金收益差异，以服务端“行动后仍有合法出口”校验防死局，不再把全部方案压成同成本。
- 模拟器加入调查、风险预案、视觉测试、跳过、收入和延迟事件；用多种可解释策略代理比较，而不是均匀随机选择证明无支配策略。
- 只在模拟发现支配项、不可达路线或现金失效时调整数值；不为了制造波动而随机惩罚玩家。

#### B3. 视觉、文本与重玩（`VIS-01`、`COPY-01`、`REPLAY-01`）

- 正式版本只保留已经批准的三套视觉系统；统一方案图、触点预览、诊断属性和结算引用，其他草稿不进入生产统计。
- 视觉测试成本、禁用状态和结果解释保持一致，并至少影响一个可追溯的顾客反应或经营指标。
- 每轮呈现全部决策问题、已知事实和当前现场变化，删除内部制作提示、空概念板块和不指向经营冲突的口号式文本。
- 报告完成后才能创建 `replay`；重玩使用独立日志、快照和报告，教师聚合默认只统计 `first_run`。

退出证据：六类策略代理均能完成 12 轮且产生可解释差异；项目负责人逐轮确认“现在发生了什么、为什么要决定、收入和代价在哪里”，并能在正式界面区分三套视觉方案和至少三条经营路径。该证据不等价于真实玩家理解度验证。

### 7.5 C 阶段：生产环境和数据安全建设

#### C1. 可重复部署（`RELEASE-001`）

- 建立独立预发布与生产配置；生产仅接受明确域名的 HTTPS 请求，CORS 不使用通配，缺少数据库、内容校验和或密钥时拒绝启动。
- 发布产物记录 Git 提交、应用版本、引擎版本、内容版本与 SHA-256、迁移版本、构建时间和资产清单。
- 健康检查区分“进程存活”和“可接收游戏动作”；数据库或正式内容不可用时 readiness 必须失败。

#### C2. 备份、恢复与观测（`OPS-002`、`OPS-003`）

- 配置数据库定时备份和内容包独立归档，在临时环境完成一次真实恢复，不以“备份文件存在”代替恢复成功。
- 监测加入失败率、动作冲突、outbox 积压、结算失败、报告生成失败、数据库连接和备份状态；日志只保留匿名 playthrough ID、请求 ID 和动作序号。
- 发现状态哈希不一致时停止新动作写入并保留证据，不自动覆盖服务端或客户端历史。

#### C3. 安全与隐私（`SEC-001`、`PRIV-001`）

- 复核教师越权、他班数据访问、身份枚举、XSS/CSRF、SQL 注入、Cookie、限速、CSV 注入和依赖风险。
- 明确姓名、学号和反思文本的用途、可见角色、保留期、整班删除/匿名化以及备份中的处理边界。

退出证据：中高危问题为零；应用和错误日志抽查无姓名学号；备份恢复后的抽样重放哈希与发布前一致。

### 7.6 D 阶段：候选版验收，不重复做无意义回归

#### D1. 真机与弱网（`QA-001`、`QA-002`）

- 真实 iPhone Safari、Android Chrome、微信内置浏览器各跑一次同一关键路径：加入 → 调查 → 选择 → 结果 → 章节复盘 → 刷新恢复 → 报告。
- 故障注入只复验 A 阶段的五个动作风险，并增加数据库短暂不可用和旧内容包两项服务端风险。
- 记录设备、系统、浏览器版本和候选构建号；模拟器结果不能替代真机签字。

#### D2. 80 人目标环境演练（`PERF-001`、`PILOT-004`）

- 80 人在 5 分钟内加入、40 个并发活跃、轮末突发提交，同时刷新教师总览和导出。
- 放行门槛沿用开发计划：健康请求 p95 < 300 ms，普通读写 p95 < 800 ms，结算 p95 < 1.5 s，错误率 < 1%，且重复结算、身份串线、首局覆盖和数据库锁死均为零。
- 演练结束执行应用重启、数据库恢复和随机局重放，确认性能通过没有掩盖数据错误。

#### D3. 脚本化全流程与项目终审（`AUTO-PLAY-01`、`PILOT-001`）

取消组织真人试玩后，建立六类**确定性策略代理**，每类保存动作日志、最终哈希、现金账本、路线、结局和报告关键断言：

1. 最少调查、优先立即收入；
2. 充分调查、保守承诺；
3. 视觉优先、重视一致性；
4. 低价促销、追求转化；
5. 高价产品、重视交付；
6. 极限资源路径：主动制造低行动力和低现金，但仍必须存在合法出口。

策略代理必须实际经过调查、风险预案、视觉测试、跳过、结果确认、章节复盘、刷新恢复和报告，不允许直接调用“选一个选择并跳到下一轮”的捷径。它们用于发现不可达路线、资源死局、支配策略和报告错配，不用来推断玩家是否喜欢游戏。

项目负责人在正式界面逐轮完成 12 轮走查，确认地域文化、商业事实、理论因果、视觉方向、现场文本和作业迁移；`docs/content-review-v11.md` 不得保留“待审”。若项目负责人决定跳过某项内容审阅，必须在发布风险清单中记录具体轮次和原因，不能默认为通过。

退出证据：六类代理全部完成、状态可重放、至少三条路线可达且没有单一策略在现金和四维评分上同时占优；项目负责人终审签字完成。

### 7.7 E 阶段：冻结、Go/No-Go 与上线操作

#### E1. 正式冻结（`RELEASE-002`）

封存以下内容为一个不可拆分的发布清单：应用镜像、数据库迁移、内容包、内容校验和、引擎版本、资产清单、环境配置模板、真机/负载/恢复记录、课程签字和已知低风险问题。旧版 `docs/v1.1-release-candidate-report.md` 不作为 v1.2.0 的放行证据，应由当前候选版报告替代。

#### E2. Go/No-Go 条件

以下任何一项出现即为 **No-Go**：

- 存在未关闭的 P0/P1，或出现任意一次重复扣费、重复结算、动作丢失、首局覆盖、身份串线、状态/报告哈希不一致；
- 正式内容版本或校验和不一致，项目内容仍有未签字或未记录风险的项目；
- 生产备份无法恢复，或恢复后不能重放得到相同结果；
- 真机关键路径阻断，80 人演练超过既定错误率/延迟门槛；
- 日志、URL、匿名案例或投影中出现姓名、学号等 PII；
- 无法回退应用镜像且保证历史动作日志不被改写。

只有技术负责人确认 A—D 证据、项目负责人确认内容并书面接受“未经过组织试玩”的剩余风险、部署负责人确认恢复与监控后，才可创建正式班级。

#### E3. 上线当天最小操作手册

| 时间点     | 操作                                                                                      | 失败处理                                                         |
| ---------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| T-1 天     | 冻结内容和构建；备份；在正式域名用测试班级完成冒烟后清除整个测试班级                      | 任一版本号、校验和或恢复结果不一致则停止发布                     |

### 7.11 取消试玩后的剩余风险声明

直接建设可以把流程可靠性、数据一致性、资源可达性、跨设备运行和发布恢复做到工程可验证，但以下结论在没有真人试玩时保持**未知**：

- 新玩家是否能在没有解释的情况下理解第一轮目标；
- 12 轮真实完成时长是否集中在 35—50 分钟；
- 玩家是否感到收入反馈有激励、选项有真实取舍而非考试题；
- 三套视觉方向是否在真实观察中足够可辨认；
- 报告是否真的帮助学生形成课程理解和课堂讨论。

因此最终版本可标记为“**工程发布版 / 未经组织试玩验证**”，不能在文档中写成“可用性与教学效果已验证”。若上线后从真实课堂首次获得这些反馈，应作为新版本输入，不原位修改已发布内容或历史结果。
