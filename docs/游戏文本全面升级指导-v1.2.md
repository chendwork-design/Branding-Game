# 《老街品牌局》游戏文本全面升级指导 v1.2

> 文档性质：玩家文本审计、改写规范与执行清单  
> 适用版本：PRD v1.1 之后的下一轮内容升级  
> 审计对象：学生加入页、序章、HUD、经营看板、回合简报、行动与情报、战略选择、视觉比较、结果反馈、结局报告及玩家可见错误提示  
> 核心目标：让学生先看懂正在发生什么、再理解自己为何要选，最后在报告中学会用课程概念解释后果。

## 1. 本轮升级结论

当前文本已经具备完整的课程知识框架，但玩家层仍有五类明显问题：

1. 专业词汇常直接出现，学生必须先懂理论，才能看懂游戏。
2. 一些句子省略了比较对象、行动对象或前文指代，导致涵义断裂。
3. 部分台词看似口语，实际不符合日常中文的表达逻辑。
4. 大量抽象名词和被动句削弱了“谁做了什么、谁受到了影响”的因果感。
5. 服务端、同步、内容版本、正式记录等后台信息进入玩家界面，破坏沉浸感。

本轮不能只做“润色”。需要同时升级内容结构、术语解释机制、界面呈现和自动检查规则。

最终应形成以下体验：

> 玩家看到具体现场 → 明白要解决什么问题 → 花资源取得具体结果 → 比较几条现实方案 → 看到顾客或店铺发生变化 → 报告再告诉他这件事在课程里叫什么。

玩家不需要先背会“品牌承诺”“视觉语义”“品牌人格”等术语，才能做出有意义的选择。

## 2. 已确认的产品边界

以下决定作为文本升级的前提，不在本轮重新讨论：

- R01、R02、R03、R04、R05、R08、R12 必须完成战略选择。
- R06、R07、R09、R10、R11 可以选择“跳过本轮战略选择”，跳过后直接进入本轮结果，不是暂缓。
- 每轮 6 点行动力中，2 点固定保留给战略选择，4 点可用于调查、测试、准备或预案。
- 学生在 R05 自行填写品牌名。
- 品牌名不调用 AI 或外部 API，不评价名称“高级不高级”；系统只检查是否完成命名、玩家声明的命名意图，以及名称是否被持续应用到相关触点。
- IP 是可选路线，不强迫所有视觉提案都配置 IP。
- 三类视觉路线必须在图形上真正不同：文字标志系统、符号系统、IP 角色系统。
- 调查和行动不机械地混成一种按钮。免费事实负责交代已知现场；付费调查揭示证据；测试或准备行动改变经营条件；战略选择负责确定本轮路线。

## 3. 文本分层：同一件事不能用同一种话说到底

游戏至少需要区分五种语言层。每一层承担不同任务。

| 文本层 | 面向谁     | 主要任务                           | 推荐语气               | 禁止事项                 |
| ------ | ---------- | ---------------------------------- | ---------------------- | ------------------------ |
| 剧情层 | 玩家       | 交代人物、现场和冲突               | 自然、具体、有轻微幽默 | 堆课程术语、讲后台规则   |
| 操作层 | 玩家       | 告诉玩家能做什么、花什么、得到什么 | 短、主动、可执行       | 抽象口号、模糊动词       |
| 规则层 | 玩家       | 说明资源、限制、输赢和不可逆后果   | 直接、无歧义           | 用梗代替规则             |
| 反馈层 | 玩家       | 说明谁发生了什么变化               | 具体、有即时感         | 只报“指标上升”           |
| 教学层 | 玩家与教师 | 解释因果和课程理论                 | 准确、完整、可回指证据 | 把理论结论伪装成剧情事实 |

教师后台和技术诊断属于第六层，不得与以上五层混写。内容版本、服务器状态、动作编号和审计记录只应存在于教师视图、技术日志或“关于游戏”页面。

## 4. 五项强制文本标准

### 4.1 专业术语必须“先讲人话，再给名称”

首次出现专业术语时，采用三步结构：

1. 先提出玩家已经能理解的现实问题。
2. 再给出术语名称。
3. 最后用一句话说明它会影响什么选择。

推荐形式：

> 你准备向顾客保证什么？  
> 品牌承诺：顾客每次购买时，都可以期待你稳定做到的事。  
> 这项承诺会影响产品、价格、服务和之后的口碑。

错误形式：

> 请确定品牌承诺，并提升承诺可信度。

#### 手机端首次解释方式

- 首次出现时，在术语后显示一个“？”或带虚线下划线。
- 玩家点按后，从底部弹出一张不超过半屏的解释卡。
- 解释卡固定包含“简单说”“在本局里”“看一个例子”三项。
- 每个页面最多主动展开一个新术语，避免连续弹窗。
- 玩家关闭后，本局不再自动弹出，但可以从经营看板的“概念小抄”再次查看。
- 角色台词优先说人话，系统说明再显示术语。
- 最终报告每次使用核心术语时仍要补充本局语境，不能假设玩家已经完全掌握。

### 4.2 每句话必须有完整上下文

凡是出现“比较、支持、提醒、参与、影响、路径、机制、关系、系统、方案”等词，编辑者必须能回答：

1. 谁在做？
2. 做什么？
3. 对谁或对什么做？
4. 与谁比较，或依据什么判断？
5. 玩家需要因此改变什么决定？

如果任一答案只能靠编辑者猜测，这句话就不能进入玩家界面。

禁止使用没有前置说明的序号指代，例如“第七步”“第二阶段”“这套机制”。只有当界面刚刚展示了编号清单，而且编号仍可见时，才允许使用序号。

例如“顾客路线比较”不是完整任务：玩家不知道要比较哪些路线，也不知道比较什么。应改为：

> 比较“先做居民日常茶饮”“先做游客地标饮品”和“双时段试卖”：看看现有客流、重复购买机会和团队人手更支持哪一条。

### 4.3 口语必须符合中国人的日常表达逻辑

口语化不是把书面句子加上“啊、呢、吧”，而是让人物从自己当下的处境说话。

角色台词优先采用：

> 眼前发生的事 + 人物担心什么 + 对玩家提出一个具体问题

例如：

> 小周：订单一多，谁还有空边做饮品边讲品牌故事啊？  
> 系统说明：如果你增加现场讲解，门店工作量会上升，高峰期出杯可能变慢。

不要写：

> 故事可以慢慢讲，但高峰期谁来做第七步？

“第七步”没有前文对象，人物也不会在现实对话中这样表达。

流行梗只能放在非关键反应句中，且必须满足：

- 不影响规则理解；
- 不依赖很短命的小众热梗；
- 不挖苦玩家或把失败归因为玩家“笨”；
- 下一行必须用普通中文讲清实际后果。

### 4.4 尽量使用主动语态和具体主语

优先写“顾客、店员、供应商、合作方、平台、包装、菜单、店铺”做了什么。

| 抽象或被动写法           | 推荐写法                                                         |
| ------------------------ | ---------------------------------------------------------------- |
| 文化可信度上升           | 顾客看到茶材来源后，更愿意相信这不是临时编出来的故事             |
| 两类需求被区分管理       | 你把居民和游客安排在不同时间测试，团队终于看清两类人各自在意什么 |
| 差异化形成               | 顾客开始能说出你和隔壁茶饮店到底哪里不同                         |
| 方案得到情报支持         | 午后访谈显示，游客确实更在意地方故事和带走后的谈资               |
| 风险被暴露               | 小样测试发现，这款饮品在高峰期要多花一倍制作时间                 |
| 品牌承诺被兑现           | 店里每次都按此前说好的原料、分量和等待时间交付                   |
| IP 获得新触点            | 顾客把 IP 杯套带到车站和办公室，更多人在门店之外看见了它         |
| 洞察、产品和视觉形成闭环 | 团队把顾客反馈写进下一年的产品和视觉 brief                       |

指标名称可以保留专业准确性，但即时反馈必须先告诉玩家“谁发生了什么”，然后再显示数值变化。

### 4.5 玩家层不得泄露后台信息

以下词语原则上不得出现在学生游玩流程：

- 服务端、客户端；
- 正式结算、权威结算；
- 内容版本、规则版本、协议版本、校验和；
- 同步到服务器、本机存档、本地状态；
- action ID、trace、决策记录编号；
- 报告引擎、内容包、已发布内容；
- 教师要求你模拟、系统正在计算正式结果。

必要的功能信息要换成玩家能理解、且不破坏情境的表达。

| 当前或类似表达               | 玩家层改写                                 |
| ---------------------------- | ------------------------------------------ |
| 正式学生入口                 | 学生入口                                   |
| 这是服务端正式结算入口       | 输入班级信息，接手这家屯溪老街茶饮店       |
| 正在向服务器确认本局进度     | 正在找回你上次离开的进度……                 |
| 服务器已同步                 | 进度已记下                                 |
| 本地已保存                   | 进度已记下                                 |
| 内容版本已经更新             | 游戏内容已更新，请刷新页面后重新进入班级   |
| 学生端与服务器内容版本不一致 | 页面内容已更新，请刷新后再试               |
| 本机存档与服务器不兼容       | 上次停留的页面已经过期，正在从最近进度继续 |
| 第 7 条决策记录              | 第 7 轮：服务也是品牌的一部分              |
| 每个动作都会保存到首局记录   | 离开页面后，下次还能从这里继续             |

技术信息若确实需要帮助排错，应放在可展开的“错误详情”中，并默认收起。玩家首先看到的必须是“发生了什么”和“现在可以怎么做”。

### 5.1 术语卡示例

标题：品牌人格

简单说：如果这家店像一个人，它会怎么说话、怎么待客？

在本局里：你选择的语气不能只出现在海报上，店员招呼、菜单说明和处理差评时也要保持一致。

看一个例子：海报说“像街坊一样亲切”，但店员回答问题时冷冰冰，顾客就会觉得品牌只是在演。

## 6. 逐屏文本审计与改写方案

### 6.1 加入页与恢复页

当前问题：

- “正式学生入口”“服务端正式结算”把技术架构暴露给玩家。
- “首局记录”是教师和审计视角，不是玩家视角。
- “授权视图、匿名案例、公开页面或网址”准确但太像隐私政策。

建议改为：

> 屯溪老街 · 品牌经营体验  
> 加入老街品牌局  
> 输入班级信息，接手这家屯溪老街茶饮店。离开页面后，下次还能从这里继续。

按钮：

> 进入品牌局

隐私提示：

> 姓名和学号只供任课教师确认身份；课堂展示不会显示你的姓名和学号。

恢复页：

> 正在找回你上次离开的进度……  
> 马上回到店里。

### 6.2 序章与获胜说明

序章必须在三屏内回答：

1. 你扮演谁？
2. 你要经营什么？
3. 怎样才算赢？

推荐文案：

> 你接手了一家准备开在屯溪老街的茶饮店。接下来一年，你要决定服务谁、卖什么、怎么定价、长什么样，以及店火了以后能不能接得住。

> 这不是“现金最多就赢”。最终排名会同时看四件事：店有没有活下来、顾客是否愿意买和再来、品牌是否让人记得住、店里能否一直做到自己答应的事。

> 每一项选择都会消耗现金、行动力和时间。有些效果立刻出现，有些问题会过几轮才回来找你。

避免：

> 前后矛盾会产生真实代价。  
> 让顾客、现金、品牌和交付一起站得住，最后按整局路径形成结局。

后一句可以作为内部设计说明，但玩家需要更直接的获胜条件和指标对象。

### 6.3 HUD 与经营看板

HUD 只保留玩家此刻需要决定的信息：

- 现金：还能投入多少；
- 自由行动：本轮还可调查、测试或准备几次；
- 战略行动：保留 4 AP，方案按复杂度消耗 2—4 AP；
- 当前日期或经营阶段；
- 看店铺状态。

不得在主 HUD 显示 v1.1、服务器已同步或本地已保存。保存状态只在发生保存或恢复时短暂提示“进度已记下”。

指标必须分成“顾客怎么回应”和“店里能不能接住”。每项采用：

> 数值 + 状态段位 + 一句对象明确的解释

例如：

> 交付能力 62｜基本够用  
> 普通客流时能稳定出杯；如果订单突然翻倍，等待时间会明显增加。

进度条建议设置五个可理解区间：

| 数值   | 状态     | 玩家理解                   |
| ------ | -------- | -------------------------- |
| 0–19   | 已经失控 | 当前问题正在直接伤害经营   |
| 20–39  | 明显吃紧 | 再增加工作量很可能出问题   |
| 40–59  | 勉强够用 | 能维持现状，不适合贸然扩张 |
| 60–79  | 基本稳住 | 可承接适度增长，仍需留缓冲 |
| 80–100 | 很稳     | 当前条件下有较强承接余量   |

“承诺可信度”“品牌一致性”等专业指标第一次展开时调用术语卡，不要求在窄屏中长期显示整段解释。

### 6.4 本轮目标

“现场、为什么现在、两难”的结构可以保留，但必须全部具体化。

推荐结构：

- 发生了什么：具体人物、数字或经营变化；
- 现在必须决定什么：不决定会发生什么；
- 你要在什么之间取舍：明确列出两个或三个方向；
- 完成本轮：用一个主动动词描述。

示例：

> 发生了什么：中午居民排队，下午游客进店拍照，但两类人点的产品几乎不一样。  
> 为什么现在要选：菜单和首批原料明天就要下单，再拖一天会增加成本。  
> 你要取舍：先服务附近居民、先做游客地标饮品，还是用两个时段小规模试卖。  
> 本轮要完成：确定第一批最优先服务的顾客。

“本轮目标”插图必须展示冲突本身，例如两类客流、排队、后厨工作量或视觉触点，不只放装饰性街景。

### 6.5 行动与调查

当前“先行动，还是先问清楚”“可以做什么”“可选信息”把同一轮拆成两个相互较弱的清单，容易让玩家感觉行动只是空耗资源。

推荐按“本轮需要回答的问题”分为 2–3 个问题组，而不是按调查方法分组。

例如 R01：

#### 问题一：谁更可能稳定来买？

- 免费已知：上午居民经过较多，下午游客停留更久。
- 调查：观察不同时段客流。
- 调查所得：两类人的购买时间、停留时间和购买原因。
- 它帮助比较：居民优先、游客优先、双时段试卖。

#### 问题二：两类顾客各自在意什么？

- 调查：做五次短访谈。
- 调查所得：居民在意稳定和方便；游客在意地方感和带走后的谈资。
- 它帮助比较：产品价值和传播语言。

#### 问题三：店里能不能同时服务两类人？

- 准备行动：盘点两个人的工作时间和制作步骤。
- 行动所得：双线运营会增加多少工作量。
- 它帮助比较：双时段试卖是否需要风险预案。

每个付费行动必须在按钮附近说明：

- 要做什么；
- 花费多少现金、自由行动力和天数；
- 完成后会得到什么；
- 主要帮助比较哪些战略选项。

禁止继续使用跨回合复用的空泛模板：

- 做一次现场观察；
- 做一个小范围测试；
- 把投入和限制问清楚；
- 先收集与本轮目标直接相关的事实。

这些模板必须改成每轮独立的动作和产出。例如：

> 记录两个时段各 20 名路人的停留与购买  
> 花费：1 自由行动｜1 天  
> 得到：居民与游客的到店时段、停留时间和购买原因  
> 帮助比较：居民优先、游客优先、双时段试卖

### 6.6 情报结果

“事实—意味着—还不知道”可以保留，但必须给“意味着”添加明确主语和决策对象。

当前：

> 日常场景访谈支持先把服务对象说窄。

建议：

> 访谈显示，附近居民更常重复购买。这个结果更支持“先服务附近居民”，但还不能证明游客不会买。

当前：

> 团队容量提醒双线定位需要额外防护。

建议：

> 两个人无法同时维护两套产品和两种讲解方式。如果选择“双时段试卖”，你最好先减少产品数量或安排额外人手。

关系标签不得只显示“支持、提醒、背景”。应显示：

- 更支持哪项选择；
- 提醒哪项选择存在什么风险；
- 只是补充哪项判断，为什么还不能下结论。

### 6.7 行动力不足与战略保留

行动力提示要用资源后果说话，不能只显示按钮变灰。

在自由行动只剩 1 点时：

> 只剩 1 点自由行动力。继续调查后，你本轮将不能再做其他调查或准备；4 点战略行动已经为最后的选择保留。

当玩家试图执行超出自由额度的行动时：

> 这项行动需要 2 点自由行动力，你现在只剩 1 点。可以先去做战略选择，或改选一项 1 点行动。

必须完成战略选择的回合：

> 这一轮必须确定方向，才能继续经营。

允许跳过的回合：

> 你可以跳过本轮战略选择。跳过后，本轮不会执行任何新方案，也不会退还已经花在调查和准备上的资源。

确认按钮：

> 确认跳过本轮

二次确认：

> 这不是暂缓。确认后将直接结算本轮，你本轮不会获得战略方案带来的收益，也不会承担该方案的直接成本。

### 6.8 战略方案与详情

战略选择页不应写成问卷。列表卡只显示：

- 方案名称；
- 一句具体做法；
- 现金、战略行动力、准备天数、工作量；
- 最明显的收益与风险各一个。

点开详情后再显示完整内容、情报关系、预案和课程概念。

“已有情报是否支持”建议改为：

> 你掌握的信息怎么说

三种状态：

- 已查看并支持：你看过“午后购买访谈”，其中的游客需求更支持这项选择。
- 已查看但提醒风险：你看过“团队时间盘点”，它提醒这项选择会让两个人同时维护更多工作。
- 尚未调查：你还没有调查与这项选择直接相关的问题，执行时要承担更多不确定性。

“现在，你愿意押注哪条路？”可以保留为气氛文案，但下方要紧接清楚规则：

> 选择一项本轮要执行的经营方案。每项方案都能推进游戏，但会带来不同成本和后果。

### 6.9 角色台词

每条角色台词必须依附于具体现场。推荐格式：

> 人物反应：一句自然口语。  
> 玩家要点：一句清楚规则。

改写示例：

| 问题句                                     | 推荐改写                                                                     |
| ------------------------------------------ | ---------------------------------------------------------------------------- |
| 故事可以慢慢讲，但高峰期谁来做第七步？     | 小周：订单一多，谁还有空边做饮品边讲品牌故事啊？                             |
| 共享体验会共享声誉风险                     | 合作店老板：顾客不会管是哪家出的错，杯子漏了，两家的名字都会一起被骂。       |
| 品牌进入新的旅行触点                       | 游客把杯套带上高铁，同行的人第一次在老街之外看见了你的品牌。                 |
| 文化来源有了具体说法                       | 店员现在能说清这款茶来自哪里、为什么这样配，顾客也更愿意相信这个故事。       |
| 这一步已经有了暂时答案，但经营会继续检验它 | 你先定下了方向。下一轮开始后，顾客和店员会用真实反应告诉你这条路走不走得通。 |

同一人物要维持稳定语气。建议建立角色语气表：

- 店员小周：直接、关心忙不忙得过来，不讲理论词。
- 设计师阿岚：会用视觉专业词，但先举店招、杯体、头像等具体例子。
- 供应商程师傅：关心批次、原料、交期和可追溯信息。
- 游客顾客：关心能不能快速看懂、拍照、携带和复述。
- 居民顾客：关心稳定、方便、价格和下次还会不会一样。

### 6.10 视觉提案比较

当前：

> 这一屏模拟老师要求你把 LOGO、VI、IP 或包装放进多个触点中判断。

这句话直接暴露课堂模拟。建议改为：

> 把同一套设计放进店招、杯体、包装和手机头像里看看：离开效果图后，它还认得出来、用得顺吗？

比较页必须先展示真实示意图，再显示解释。三个方向分别至少展示：

- 店招；
- 杯体或杯套；
- 外带包装；
- 手机头像或社交页面。

三类方案的文字说明：

1. 文字标志系统：没有 IP，强调店名是否易读、缩小后是否清楚。
2. 符号系统：没有 IP，强调图形是否易认、会不会和同街常见徽派符号混淆。
3. IP 角色系统：强调角色性格、动作规范和使用任务，也明确维护成本。

视觉术语必须服务比较：

> 视觉语义：这套棕色手写字让人觉得亲切、手作，但也可能让游客误以为产品价格更高。  
> 视觉适配：缩成手机头像后仍能认出，印在杯套侧面时部分文字会被手挡住。

禁止：

- 只用“高级、年轻、国潮、有文化”评价方案；
- 三套提案只换颜色或装饰图；
- 让系统评价玩家自填品牌名的语义质量；
- 先显示理论长文，再让玩家找图。

### 6.11 执行结果页

结果页先回答“发生了什么”，再回答“为什么”。

推荐信息顺序：

1. 一张结果图或短动效；
2. 角色的一句即时反应；
3. 顾客变化；
4. 店铺变化；
5. 现金、时间和指标变化；
6. 可展开的因果解释；
7. 延迟风险提示。

当前：

> 指标即时变化：文化可信度 +8。

建议：

> 顾客终于听到了能核对的茶材来源。  
> 文化可信度 +8

当前：

> 这项决定先改变了资源分配，效果将在后续经营中显现。

建议：

> 你已经花掉预算并占用了团队时间，但顾客还没看到变化。等方案进入门店后，效果才会出现。

“为什么会这样”默认折叠是合理的。展开后采用：

> 你的选择 → 先改变什么 → 谁作出反应 → 哪项后果延迟出现 → 对应课程概念

### 6.12 结局与报告

报告允许使用课程术语，但必须把术语锚定到玩家本局证据。

当前：

> 一笔成街在本局路径中的触点适配分为 72；它不是单独的美观评分，而是与定位、产品、客群和使用场景共同形成的诊断。

建议：

> 这套视觉的触点适配得分是 72。系统检查了它是否适合你选择的顾客、产品和价格，以及放在店招、杯体、包装和头像中是否仍然清楚。这不是单纯的美观分。

当前：

> “设计进入现实”在本局留下的可观察变化最多，适合拿来复盘选择、机制和后果之间的关系。

建议：

> “设计进入现实”这一轮让店铺变化最明显。回头看看：你当时依据了什么、付出了什么，后果又在哪一轮出现？

证据诊断应保留，但换成更容易理解的标签：

| 当前标签         | 玩家报告标签           | 解释                                             |
| ---------------- | ---------------------- | ------------------------------------------------ |
| 依据证据         | 看过并用上了相关信息   | 你查看的信息与最终选择方向一致                   |
| 只采用了部分证据 | 用上了一部分信息       | 你采用了支持信息，但没有处理其他提醒             |
| 看过信息但未采用 | 看过，但选择了另一条路 | 这不自动等于错误，报告要说明你承担了什么不确定性 |
| 凭直觉或情境判断 | 没有查看直接相关的信息 | 你可以这样选，但较难解释判断依据                 |
| 尚未形成正式选择 | 本轮没有执行战略方案   | 仅适用于允许跳过的回合                           |

“第 N 条决策记录”不得显示给学生。改成“第 N 轮·回合标题”。原始序号只留在教师授权视图和审计数据中。

### 6.13 操作 Toast、资源不足与异常提示

当前引擎把技术动作的 `trace.explanation` 直接放进学生端 Toast。这样虽然便于开发调试，却会把“提交、记录、ID、同步”等后台视角带进游戏。升级后，操作反馈应说明玩家刚做成了什么，以及下一步能做什么。

| 当前表达                             | 问题                                   | 玩家层改写                                                                     |
| ------------------------------------ | -------------------------------------- | ------------------------------------------------------------------------------ |
| 完成了行动：观察不同时段客流         | 只重复按钮名，没有反馈产出             | 客流记录拿到了。现在可以比较居民和游客分别在什么时候来、为什么买。             |
| 看完了调查：午后购买访谈             | “看完”不是经营结果                     | 访谈整理好了。展开看看它更支持哪项方案、又提醒了什么风险。                     |
| 比较了一项方案，但还没有正式提交     | 暴露提交状态，且预览不需要打断玩家     | 不弹 Toast；用方案卡的“已预选”状态反馈即可。                                   |
| 执行了“某方案”，结果等待确认         | 像流程日志                             | 方案已经开始执行。先看看顾客和店里发生了什么。                                 |
| 完成了视觉测试：vt-r08-sign          | 把内部 ID 显示给玩家                   | 店招三秒测试完成：路人能否认出店名和品类，结果已经记下。                       |

| 现金不够，不能执行这项投入           | 缺少差额和替代动作                     | 这项方案还差 ¥8,000。可以换一项投入更小的方案，或不再增加预案。                |
| 请先确认本轮结果                     | 规则正确但语气生硬                     | 先看完这一轮发生了什么，再进入下一步。                                         |

加入与恢复错误也要从“系统诊断”改成“玩家如何继续”：

| 当前表达                         | 首屏玩家提示                                                           | 可折叠技术详情                      |
| -------------------------------- | ---------------------------------------------------------------------- | ----------------------------------- |
| 班级不存在或已关闭               | 没找到这个可加入的班级。请核对班级码，或问问任课教师是否已经开放。     | `CLASS_NOT_FOUND`                   |

### 6.14 R05 自填品牌名的文本规则

品牌名由学生自行填写，但本游戏不调用 AI 或外部 API 评价名字，也不判断名字“高级不高级”。文本必须把玩家的任务说成“声明意图并持续使用”，而不是“猜系统喜欢什么名字”。

建议流程：

1. 输入名称：`这家店叫什么？`，限制 2–12 个汉字或合理长度的中英文组合。
2. 选择或填写命名意图：`你希望顾客先从名字里想到什么？`，例如日常亲切、地方来源、轻松年轻、专业克制。
3. 选择品牌人格：`如果这家店像一个人，它会怎样和顾客说话？`，首次点开术语卡解释“品牌人格”。
4. 后续视觉、菜单、包装和服务文案都带入该名称；系统只检查是否可读、是否在触点中持续使用、是否与玩家自己声明的意图一致。

首次提示推荐：

> 名字没有标准答案，系统也不会替你评审“好不好听”。你要先说清希望它给顾客什么感觉，后面的 LOGO、包装和服务会继续检验你有没有把这件事做到底。

禁止出现：

- AI 正在分析你的品牌名；
- 系统认为这个名字缺乏高级感；
- 该名称与黄山文化匹配度 82%；
- 使用热门词可自动增加知名度。

如果需要基础安全检查，只做本地、确定性的格式校验和课堂禁用词过滤；这不属于品牌质量评分，也不消耗模型算力。

### 6.15 成批模板必须重写，不能只做同义替换

当前 48 个方案采用：

> 做法。风险会在后续经营中继续检验这项取舍。

这类句子既重复，又经常形成“会……会……”的语法问题，也没有告诉玩家后果由谁触发、何时出现。每个方案应拆成三个独立字段：

- `playerConsequence`：执行后谁会立刻看到什么变化；
- `delayedRisk`：什么条件下，哪一类问题会在后续回合出现；
- `reportMechanism`：局后用课程概念解释因果，但必须回指本局证据。

示例：

当前：

> 用两套入口扩大机会面。资源不足时容易两头不稳会在后续经营中继续检验这项取舍。

游戏结果页：

> 居民和游客都找到了适合自己的入口，但两名店员现在要维护两套产品说明和服务节奏。

延迟伏笔：

> 如果下一轮不减少产品数量或补充人手，高峰期更容易出现错单和等待。

报告解释：

> 你扩大了目标场景，却没有同步增加组织承接力。因此客群覆盖先上升，交付压力随后出现。这对应“定位范围必须与组织能力匹配”。

同样，48 条“你的品牌作业能否说明……”不能只替换方案名。每轮复盘题要对应当轮真实矛盾：

- R01：你凭什么判断第一批顾客值得优先服务？
- R03：主打产品的哪个步骤最可能拖慢高峰出杯？
- R05：你的 LOGO、辅助图形和 IP 分别负责什么，是否有重复？
- R08：离开大幅效果图后，哪一个触点最先暴露视觉问题？
- R11：如果订单再增加一倍，团队会先在哪个环节失控？

### 6.17 角色口语的句式模板

角色不负责讲完整理论，只负责把现实压力说出来。优先使用以下句式：

- 店员：`现在一到____，我们就____。如果再加____，最先忙不过来的是____。`
- 顾客：`我会因为____第一次买，但下次还来，要看____。`
- 供应商：`这个做法能做，不过每批至少____，交期要____。`
- 设计师：`放在大海报上没问题；缩到____以后，____会先看不见。`
- 合作方：`我可以把顾客带来，但如果____出了问题，他们也会来找我。`

系统说明紧跟角色反应，用主动句还原机制：

> 小周：订单一多，谁还有空边做饮品边讲品牌故事啊？  
> 系统说明：增加现场讲解会占用店员时间。高峰期如果不减少产品步骤，顾客会等得更久。

不要让角色说“承接力下降、触点失配、关系资产受损”。这些词可以在指标和报告中出现，但必须先由角色说出可观察的现场。

## 7. 当前内容中需要成批替换的表达模式

### 7.1 空泛行动模板

下列模板在不同回合重复出现，必须逐轮重写：

- 做一次现场观察；
- 做一个小范围测试；
- 把投入和限制问清楚；
- 先收集与某目标直接相关的事实。

每条新行动必须绑定一个具体问题、动作数量、参与对象和产出。

### 7.2 抽象结果标签

以下内容不能单独作为玩家反馈：

- 文化可信度上升；
- 视觉资产和关系传播延展；
- 洞察、产品和视觉形成闭环；
- 品牌承诺有了持续复盘的依据；
- 价格解释更有层次；
- 共享体验会共享声誉风险；
- 平台规则成为新的经营变量。

可以保留为内部指标摘要，但玩家层必须补充具体主体和场景。

### 7.3 模板化角色反应

当前类似：

> 这一步先记下来：某目标已经有了一个暂时答案，但经营会继续检验它。

这种句子每轮都适用，因此没有人物性格，也没有事件信息。每轮至少需要：

- 一条与本轮结果绑定的角色反应；
- 一条与玩家选择绑定的具体后果；
- 如果有延迟效果，一条自然的伏笔。

## 8. 数据结构与界面建设路径

### 8.1 建立统一术语表

新增 TermGlossaryEntry：

| 字段              | 用途               |
| ----------------- | ------------------ |
| termId            | 稳定标识           |
| term              | 专业名称           |
| plainDefinition   | 一句人话解释       |
| inGameMeaning     | 在本局里影响什么   |
| example           | 一个具体例子       |
| firstUseRoundId   | 首次允许出现的回合 |
| relatedMetricKeys | 关联指标           |
| relatedTheoryIds  | 关联课程理论       |

内容中的专业词通过 termRefs 引用术语表。构建时检查：

- 每个 termRef 都能找到定义；
- 术语不得早于 firstUseRoundId 无解释出现；
- 首次出现页面必须提供解释入口。

### 8.2 将玩家文案与内部描述分开

建议给关键内容对象拆出：

- playerLabel：玩家看到的短标题；
- playerDescription：玩家看到的具体说明；
- characterLine：角色反应；
- playerConsequence：结果页的具体后果；
- reportExplanation：报告中的因果与理论解释；
- teacherExplanation：教师后台的教学补充；
- internalNote：编辑、审计或技术说明，不下发玩家界面。

不能继续让 reportExplanation、内部状态消息或技术异常直接回流到玩家提示。

### 8.3 为比较与关系补充明确字段

调查与证据建议补充：

- questionAnswered：它回答什么问题；
- comparedChoices：它帮助比较哪些方案；
- supportsChoiceIds：更支持哪些方案；
- warnsChoiceIds：提醒哪些方案的什么风险；
- remainingUnknown：看完以后仍然不知道什么。

界面根据结构化关系生成清楚句子，不再只显示“支持”“提醒”“背景”。

### 8.4 首次解释状态

增加 introducedTermIds，用于记录本局已经主动介绍过的术语。

- 只控制是否自动展开，不控制玩家是否能再次查看；
- 它不参与分数，不属于教学评价；
- 刷新后保持，避免同一术语反复弹出；
- 报告不依赖该状态，报告按需要重新解释。

### 8.5 玩家错误与技术错误分离

API 或流程层返回：

- playerMessage：可理解的处理办法；
- technicalCode：教师或开发排错使用；
- retryable：是否显示“再试一次”；
- recoveryAction：刷新、重新加入、回到最近进度或联系教师。

玩家页面默认只显示 playerMessage 和操作按钮。

- 内容版本；

- 本机存档；
- trace；
- action ID；
- 报告引擎。

允许名单仅包括教师后台、内部异常、测试、架构文档和技术日志。

### 9.2 术语首次出现测试

自动检查：

- 所有 termRefs 均存在；
- 所有困难术语均有 plainDefinition、inGameMeaning 和 example；
- 首次出现页面已挂接术语卡；
- 同一屏不得自动弹出两个以上术语卡。

### 9.3 涵义断裂扫描

将以下表达列入人工复核清单：

- 比较、支持、提醒、参与、形成、产生、得到、进入、路径、关系、机制、系统；
- 这、它、该项、上述、前者、后者；
- 第一步至第十步及阿拉伯数字步骤；
- 被、得到、得以、实现了。

这些词不是一律禁止，但每一处都必须检查主体、对象和前文指代。

### 9.4 文本长度与手机验收

建议上限：

| 文本位置       | 上限                 |
| -------------- | -------------------- |
| 回合标题       | 16 个汉字            |
| 本轮目标       | 28 个汉字            |
| 角色台词       | 45 个汉字，最多 2 句 |
| 行动名称       | 18 个汉字            |
| 行动说明       | 60 个汉字            |
| 战略方案摘要   | 36 个汉字            |
| 情报事实       | 80 个汉字            |
| 情报含义       | 70 个汉字            |
| 即时结果       | 60 个汉字            |
| 报告单段       | 120 个汉字           |
| 术语卡简单解释 | 45 个汉字            |

在 390 × 844 与 360 × 800 两种手机视口测试：

- 首屏能看到本轮目标和主要操作；

### 9.5 朗读测试

所有角色台词和关键提示都要进行人工朗读。

判断标准：

- 一口气能读完；
- 不需要回看前文才能知道“谁、什么、为什么”；
- 非设计专业学生能用自己的话复述；
- 去掉术语后，现实问题仍然成立；
- 幽默句拿掉后，规则信息仍然完整。

测试：

- 每项付费行动均有可见产出；
- 每条关系均能回指具体方案和风险；
- 行动力不足与 4 点战略保留提示完整；方案成本按 2—4 AP 显示。

验收：

- 玩家能解释“我为什么花这点行动力，它具体帮我判断了什么”。

### TEXT-005：逐轮重写剧情、角色台词与结果

建设：

- 12 轮逐句检查主语、对象、比较目标和前文指代；
- 删除无前置内容的序号和模板化角色反应；
- 把抽象指标结果改成“具体变化 + 指标”；
- 为每轮增加与选择相关的角色反应和延迟伏笔。

测试：

- 涵义断裂扫描清单归零；
- 每轮至少有一个具体现场反馈；
- 角色语气一致性人工复核。

验收：

- 学生不看指标名，也能说出本轮谁受到了什么影响。

### TEXT-006：重写视觉比较流程

建设：

- 为三类提案配置真正不同的 LOGO、VI、IP 与触点图；
- 用视觉语义和视觉适配解释比较，不用“高级、年轻、国潮”代替判断；
- 移除“模拟老师要求”等课堂后台表述。

测试：

- 每套方案至少有四个触点示意；
- 缩小、遮挡、单色和手机头像测试可见；
- IP 路线与无 IP 路线的逻辑和图形均有区别。

验收：

- 玩家能从图中指出每套方案至少一个优势和一个现实限制。

### TEXT-007：重写结果页和报告

建设：

- 结果先讲事实，再显示指标；
- 报告将每项理论回指本局选择、证据和后果；
- 改写证据判断标签；
- 隐藏决策记录编号和技术版本。

测试：

- 每轮报告具有选择、即时后果、延迟后果、证据使用、风险与理论连接；
- 所有理论结论均能回指本局数据；
- 跳过回合不会被误写为操作失败。

验收：

- 学生能用报告回答“我为什么这样选、付出了什么、后来发生了什么、课程里怎么解释”。

### TEXT-008：完整人工试玩与课堂可理解性测试

建设：

- 至少邀请 2 名未学过本课程的学生进行手机首局；
- 全程记录停顿、误解、回看、误触和无法复述的文本；
- 教师不进行现场解释，避免掩盖文本问题。

测试问题：

- 这一轮发生了什么？
- 你现在要决定什么？
- 你花行动力得到了什么？
- 这个信息更支持哪项选择，为什么？
- 你的选择让谁发生了什么变化？
- 报告里的课程概念能否对应到刚才的经历？

验收：

- 关键任务理解率 100%；
- 专业术语首次解释可找到率 100%；
- 比较对象识别率不低于 90%；
- 后台术语暴露为 0；
- 关键规则因口语或玩梗产生的误解为 0。

## 11. 完成定义

只有同时达到以下条件，本轮文本升级才算完成：

- 玩家流程中不存在后台技术表述；
- 本文术语表中的概念全部完成首次解释；
- “比较、支持、提醒”全部明确对象；
- 不存在无前文的“第几步、这个机制、这条路径”等指代；
- 关键行动全部说明具体产出和决策用途；
- 即时结果全部先描述具体对象变化，再显示指标；
- 角色台词通过朗读，不出现书面句硬改口语的情况；
- 12 轮完整报告都能回指玩家的选择、证据和后果；
- 手机窄屏中关键规则不被折叠或截断；
- 自动扫描、单元测试、流程测试和人工首局测试全部通过。

## 12. 编辑者最后检查表

每写完一条玩家文本，逐项回答：

- 学生不懂课程理论，也能看懂眼前发生了什么吗？
- 句子里是谁在做什么？
- 如果说“比较”，明确写了和谁比、比什么吗？
- 如果说“支持”，明确写了哪条信息支持哪项选择吗？
- “这、它、第几步”在当前屏幕上有清楚的前文吗？
- 能换成主动句吗？
- 这是玩家需要知道的信息，还是后台人员需要知道的信息？
- 关键规则是否被玩笑、折叠或长段落遮住？
- 学生读完能知道下一步该做什么吗？
- 这句话最终能回到具体选择、具体代价和具体后果吗？
