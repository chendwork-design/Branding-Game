# 游戏配图质量审计与下一波改进计划 v1.8

> 项目：老街品牌局  
> 审计范围：当前 v11 四回合试玩切片、视觉资产生产文档、运行时素材映射与第四回合视觉决策环节  
> 结论日期：2026-08-31  
> 执行优先级：先重做四回合试玩版中的视觉环节（内容回合 `r08`），再修复产品、包装、场景连续性和经营结果图

## 1. 结论

当前配图**没有达到 v1.5—v1.7 已经确定的目标**，不能作为正式发布给学生的版本。

问题不是图片数量不足，而是图片在游戏中承担的教学角色没有被真正实现：大量运行时图片仍然是参考图的裁切、缩放或重新编码；同一张图片被重复用于不同决策、不同回合和不同结果；稳定、吃紧、危机状态主要依靠色调覆盖；视觉方案没有形成统一的 LOGO、字体、色彩与触点系统，只是在参考照片上叠放一张小卡片。

其中最严重的是四回合试玩版中的视觉环节：

- 参考图被直接用于品牌视觉比较，违背“参考图只用于校准，不可作为正式素材”的原则；
- 三套视觉方案的画面尺寸、构图、字体、LOGO、基础色、完成度和应用场景不一致，不能形成公平比较；
- 当前的 `visual-wordmark.svg`、`visual-symbol.svg`、`visual-ip.svg` 只是概念占位卡，不是可应用的品牌视觉系统；
- 当前界面把整张方案卡叠在照片右下角，没有把 LOGO 或 IP 真正应用到招牌、杯套、外带袋、头像和小票上；
- “缩小、黑白、遮挡”测试作用在整张图片或卡片上，不能检验 LOGO 本身的识别能力；
- 结果图没有表现顾客是否更容易识别、员工是否更容易执行、触点是否保持一致，只表现了颜色变化。

因此下一波不能继续“补图”，必须先重建视觉资产生产规则与第四回合视觉比较系统。

## 3. 量化审计结果

### 3.1 参考图近似复用

- 运行时栅格图片：80 张；
- 用户参考图片：28 张；
- 与参考图感知哈希距离不大于 18 的运行时图片：49 张；
- 这些图片虽未必逐字节相同，但构图、主体、文字和版式高度一致，属于裁切、缩放、压缩或轻度处理后的参考图复用。

典型问题包括：

- `briefing-r08-visual.jpg` 与 `result-r08-*` 直接沿用绿色品牌视觉展板；
- `touchpoint-storefront.jpg` 直接沿用屯溪老街实景照片，包含原有商户招牌；
- `touchpoint-cup.jpg` 直接沿用手持成品饮料照片，并保留水印；
- `touchpoint-avatar.jpg` 实际上仍是一张品牌系统展板，并不是头像触点；
- 多个产品和包装选项直接沿用用户给出的茶饮品牌案例，没有重新生成同规格的中性方案。

### 3.2 内部重复

- 检出 19 组近似重复画面；
- 共覆盖 60/80 张运行时栅格图片；
- 同一画面最多被 7 个不同资产 ID 使用。

这会造成三个后果：

1. 玩家做出不同选择时，看见的却是同一视觉结果；
2. 图片不能帮助玩家理解选项差异；
3. 结果反馈缺乏新信息，削弱经营游戏的即时奖励感。

### 3.3 尺寸与构图不统一

当前素材比例从约 0.35 到 1.78 不等：

- 产品图同时存在 2:3、3:4 等比例；
- 包装图同时存在 0.35、0.67、0.75、0.79 等比例；
- 触点图同时存在竖图和横图；
- 回合简报与结果图混用长展板、竖版广告、方图和横版场景图。

移动端只能依靠 `object-fit: cover` 强行裁切，容易截掉产品、人物、标识或关键信息。不同方案的有效画面面积也不一致，比较结果会受到构图而非设计方案影响。

### 3.4 自动检查存在假通过

当前执行：

```text
node scripts/check-v11-assets.mjs
```

返回：

```text
v11 assets: 18 files, 16419 bytes total
```

该检查只统计 v11 根目录的少量文件，没有递归检查主要 JPG 资产，也没有检查：

- 是否复用了参考图；
- 是否存在水印、第三方品牌或可读文字；
- 是否统一尺寸；
- 是否跨用途重复；
- 是否具备稳定、吃紧、危机三个不同状态；
- 三套视觉方案是否使用同一触点和同一构图；
- 移动端关键区域是否被裁切。

所以当前“脚本通过”不代表视觉资产达标。

视觉生产缓存已经成功分流至：

```text

```

临时目录、生成图片目录和 Codex 图片目录均位于 E 盘。下一波继续在每批生成前运行 `pnpm visual:cache:check`，但无需再围绕 C 盘空间设计复杂流程。

## 5. 未达标的根本原因

### 5.1 把“参考素材”与“正式素材”混在同一生产清单中

`source-manifest.md` 明确记录了大量“参考图校准/裁切场景”。这与 v1.7 的“参考图不能直接作为正式素材”冲突，导致执行层面误以为裁切和重新编码可以交付。

### 5.2 在样片验收前追求全量覆盖

原计划要求先通过样片门，再扩展到全量素材；实际却在品牌系统、产品比较和状态反馈没有通过样片验证时，就批量建立了 75 个以上资产 ID。文件数量成为完成指标，语义质量没有成为完成指标。

### 5.3 图片、字体、LOGO、IP 和界面职责没有分开

照片模型擅长生成空间、人物、材质、商品形态和动作，不擅长稳定生成中文字体、LOGO 和精确版式。当前流程让案例图同时承担照片、品牌系统、排版和 LOGO，结果不可控且无法适配玩家自填品牌名。

正确分工应为：

- ImageGen：空白门店、杯套、外带袋、手机头像载体、小票、人物与结果状态；
- SVG/HTML/CSS：LOGO、动态品牌名、字体、颜色、图形、IP、测试遮罩和触点合成；
- 游戏数据：记录玩家选了哪套系统、在哪些触点上通过或失败。

### 5.4 缺少统一母版和同源编辑

同一门店的外立面、柜台、员工制服和主要人物没有被冻结为唯一母版。结果状态也没有从同一底图进行编辑，而是复用图片后加色调。画面无法形成“这是同一家店发生的后果”的感受。

### 5.5 当前界面不是视觉测试器

当前实现把整张视觉卡片作为绝对定位的小图层叠在照片上。招牌、杯套、外带袋、头像、小票没有各自的品牌安全区和透视坐标，因此：

- LOGO 没有贴到真实触点；
- 玩家无法比较远看、近看、印刷和数字端的差异；
- 24 px、黑白和 35% 遮挡测试没有测到真正的识别对象。

### 5.6 验收脚本只验文件，不验设计

当前脚本没有递归、没有感知重复检测、没有统一尺寸检测，也没有引用来源隔离检查。人工验收清单没有被绑定到发布门。

## 6. 下一波总策略

下一波采用“先冻结规则、先重做视觉回合、再向其他回合扩散”的顺序。

### 6.1 立即冻结的规则

1. 用户参考图全部保留在 `docs/visual-references/`，不得复制到 `apps/web/public/`。
2. 参考图不能经过裁切、压缩、改色或重新编码后进入运行时。
3. 所有运行时照片必须有生成记录、提示词版本和父级母版 ID。
4. 中文文字、品牌名、LOGO、IP 和版式不得由照片模型直接绘制。
5. 同一比较组必须使用相同尺寸、机位、背景、光线、主体比例和品牌留白区。
6. 同一结果组必须从同一批准底图编辑，稳定、吃紧、危机必须改变可观察事实，不能只改色。
7. 图片未通过语义、连续性、公平性、移动裁切和版权五道验收，不得接入运行时。

### 6.2 统一资产规格

| 资产类型           |                   生产母版 |     运行时输出 | 安全区                       |
| ------------------ | -------------------------: | -------------: | ---------------------------- |
| 回合简报/经营结果  |             1280×720，16:9 |   960×540 WebP | 中央 80%，四边各留 10%       |
| 产品/包装/情报证据 |              1200×900，4:3 |   800×600 WebP | 主体位于中央 70%             |
| 五类视觉触点底图   |              1200×900，4:3 |   800×600 WebP | 每张单独记录品牌可贴附多边形 |
| 视觉系统总览板     |              1200×800，3:2 | 浏览器实时合成 | 三方案使用同一模板           |
| LOGO/字标/IP       | SVG，`viewBox 0 0 600 400` |            SVG | 禁止栅格化为照片文字         |
| 移动端预览         |               390×844 截图 |       自动截图 | 核心主体和标识不可被裁掉     |

统一基础色先固定为一套共享色板，以避免颜色本身替玩家做决定：

```text
宣纸白  #F1E9DA
墨黑    #242621
苔茶绿  #68744E
砖铜色  #A66442
深木色  #3B2B22
```

三套视觉路线首轮比较全部使用这套色板和相同品牌名。玩家是在比较识别结构和品牌人格，不是在比较“哪张图颜色更亮”。

## 7. 最高优先级：重做四回合试玩版中的视觉环节

> 本节所称“第四回合视觉环节”，指当前四回合试玩切片中的视觉决策阶段，对应内容回合 `r08`。

### 7.1 教学目标

该环节不是让玩家选一张“好看的图”，而是让玩家直观体验：

- 品牌视觉必须把品牌承诺转成可识别的视觉线索；
- 同一视觉系统要在招牌、杯套、外带袋、数字头像和小票上保持一致；
- 视觉系统不仅影响喜欢程度，还影响远距离识别、制作成本、员工执行和传播复用；
- LOGO、IP 和字体的价值不能脱离真实经营触点判断。

### 7.2 新的玩家流程

1. 玩家先看到经营事实：顾客叫不出店名、外带杯缺少记忆点、员工临时制作物料时各做各的。
2. 系统展示三套匿名视觉路线 A/B/C，不显示“正确答案”。
3. 默认展示同一个招牌触点，三套方案使用同一底图、同一尺寸和同一基础色。
4. 玩家可切换杯套、外带袋、头像和小票，查看系统一致性。
5. 玩家可进行三项免费测试：24 px 缩小、黑白打印、35% 遮挡。
6. 玩家选择一套方案并说明最看重的指标；说明采用选择题，不增加长文本输入。
7. 结算页显示顾客识别、触点一致性、制作负担和品牌资产积累的即时变化。
8. 最终报告再解释该选择与品牌识别、视觉语义、品牌人格和接触点一致性的理论关系。

### 7.3 三套视觉路线的重制定义

三套路线共享同一动态品牌名字体栈和基础色板，避免参考图中的字体与颜色差异干扰比较。品牌名使用玩家自填内容，不调用外部 API。

#### A. 线性字标系统 `v-line`

- 核心：清楚可读的动态品牌名 + 抽象的老街屋檐/街巷折线；
- 个性：克制、清楚、偏现代文化体验；
- 强项：小尺寸可读、招牌和小票执行稳定；
- 代价：情绪记忆较弱，需要持续内容积累；
- 禁止：书法字、仿古印章、完整徽派屋顶插画、复杂山水。

#### B. 杯影符号系统 `v-symbol`

- 核心：杯口椭圆、屋檐折角与茶叶负形组成唯一几何符号；
- 个性：简洁、明确、便于形成识别资产；
- 强项：头像、杯套和远距离招牌表现稳定；
- 代价：前期规范要求更高，错误缩放会破坏负形；
- 禁止：通用山峰、波浪、红色印章、现成茶壶图标。

#### C. 服务型 IP 系统 `v-character`

- 核心：由杯套轮廓、叶片配件和蒸汽动作线构成的成熟服务角色；
- 个性：友好、有行动感，但不过度幼稚；
- 强项：活动、社交内容和顾客互动；
- 代价：绘制与维护工作量更高，小尺寸必须回退到简化头像；
- 必须提供：迎客、递杯两个动作和正常、忙乱、补救三个表情；
- 禁止：盲盒比例、幼儿动画脸、与任何现有茶饮 IP 相似的服装和轮廓。

### 7.4 字体与 LOGO 的统一规则

- 三套路线的玩家品牌名均由浏览器实时排版，不把文字烘焙进照片；
- 第一版统一采用系统可用的无衬线中文粗体栈，保证 Android、iOS 和 Windows 可读；
- 路线差异由图形结构、组合关系和触点使用方式产生，不通过随意更换字体制造差异；
- LOGO 必须同时提供横式、竖式、纯符号、单色和反白版本；
- 任何版本在 24 px 高度下不得糊成色块；
- IP 路线的小尺寸头像必须使用简化头像，而不是缩小整个人物。

### 7.5 五张全新中性触点底图

这五张图片必须重新生成，禁止使用用户参考照片：

1. 屯溪老街茶饮店门头，招牌区域完全留白；
2. 500 ml 奶茶杯和空白杯套，正面品牌区留白；
3. 米白色外带纸袋，正面留白；
4. 中性手机界面和空白圆形头像位；
5. 热敏小票，抬头区域留白。

### 7.7 真实触点合成方式

每个触点保存如下数据：

```ts
type TouchpointPlacement = {
  assetId: string;
  polygon: [[number, number], [number, number], [number, number], [number, number]];
  safeInset: number;
  defaultScale: number;
  minReadablePx: number;
  foregroundMask?: string;
};
```

实现要求：

- SVG 通过触点多边形进行透视或仿射贴合；
- 标识必须被杯沿、袋口或设备等前景正确遮挡；
- 方案切换只替换视觉系统层，不替换底图；
- 五个触点的构图、光线和缩放在三套方案间完全一致；
- 玩家品牌名作为独立文本层进入三套方案，不能写死为“一盏屯溪”；
- 所有合成预览可在浏览器中实时生成，不必为每位学生生成新照片。

### 7.8 正确的三项压力测试

| 测试       | 正确实现                         | 通过条件                                  |
| ---------- | -------------------------------- | ----------------------------------------- |
| 24 px 缩小 | 只把主标识缩到实际 24 px 高度    | 仍可分辨主要轮廓或品牌名                  |
| 黑白打印   | 只将视觉系统转换为灰度，保留底图 | 主次层级不坍塌，不能只依赖颜色            |
| 35% 遮挡   | 用遮罩遮住标识面积的 35%         | 仍能从剩余轮廓识别路线；IP 可回退简化头像 |

界面不得再缩放整张触点照片，也不得把方案卡片作为测试对象。

### 9.1 自动化检查

### 9.2 人工验收

每一批资产由至少两次人工检查完成：

#### 第一次：设计验收

- 是否一眼能看出该图所表达的经营事实；
- 是否与上一张属于同一家店、同一批人物；
- 是否有真实品牌、伪文字、水印或第三方视觉特征；
- 是否使用了主动、现实、不过度戏剧化的动作；
- 是否能在手机屏幕上看清主体。

#### 第二次：教学与游戏验收

- 图片是否帮助玩家区分选项，而不是替玩家给出答案；
- 三套视觉方案是否完成度相同；
- 测试结果是否来自 LOGO/IP 本身，而非背景差异；
- 结果图是否能解释数值变化；
- 图片是否提供即时反馈和过程成就感。

### 9.3 第四回合盲测

至少邀请 5 名不了解方案命名的人进行盲测：

- 在 3 秒内指出每套方案最容易记住的元素；
- 在 24 px、黑白和 35% 遮挡条件下辨认三套方案；
- 查看五类触点后判断它们是否属于同一品牌；
- 不告知理论名词，让测试者描述三套方案的性格差异；
- 若某套方案因为图片更亮、人物更多或背景更好看而占优，必须重新制作比较矩阵。

## 10. 每批生成的执行方式

每批最多处理 3—5 张图片，遵循：

1. `pnpm visual:cache:check`；
2. 生成到 `.cache/visual-production/generated-images/<batch-id>/`；
3. 不直接覆盖 `apps/web/public/assets/v11/`；
4. 人工查看原图；
5. 运行重复、尺寸、来源和移动裁切检查；
6. 通过后写入 manifest；
7. 使用 `apply_patch` 更新运行时映射；
8. 运行相关测试；
9. 在浏览器中以 390×844 和桌面宽度各试玩一次；
10. 当前批次验收后再开始下一批。

任何失败都应退回当前批次重新生成或编辑，不得用旧参考图临时顶替。
